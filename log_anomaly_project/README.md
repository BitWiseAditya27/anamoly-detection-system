# LogSentry — ML-Based Log Anomaly & Threat Detection

A Flask web application that lets a user **upload a raw log file**, runs it through an
**unsupervised machine learning pipeline**, and flags lines that deviate from normal
behavior — surfacing potential threats (brute-force attempts, unauthorized access,
suspicious traffic) without needing any labeled training data.

## Why unsupervised learning?

Real-world logs are almost never labeled ("this line is an attack, this one isn't").
The system instead learns what *normal* looks like and flags what doesn't fit —
using **Isolation Forest**, chosen after comparing it against **Local Outlier Factor**
and **One-Class SVM** on a labeled synthetic dataset (labels used only for evaluation,
never during training).

## Results (on synthetic evaluation set, 2000 log lines / 10% injected anomalies)

| Model               | Precision | Recall | F1    | ROC-AUC |
|---------------------|-----------|--------|-------|---------|
| **Isolation Forest** | 0.81      | 0.80   | 0.81  | 0.99    |
| Local Outlier Factor | 0.15      | 0.15   | 0.15  | 0.61    |
| One-Class SVM        | 0.16      | 0.42   | 0.23  | 0.78    |

On a held-out, differently-generated batch (simulating a real upload), Isolation Forest
achieves **96% recall** — it catches nearly every real anomaly, with some false positives,
which is the right trade-off for a security-monitoring tool (missing a real threat is far
worse than an extra line for a human to review).

Full metrics are saved to `results/metrics.json` after training.

## Features engineered per log line

- **Log level score** (INFO/WARNING/ERROR/CRITICAL)
- **Message length**
- **Presence of a number** (error codes, IPs, counts)
- **Suspicious keyword count** (failure, unauthorized, blocked, injection, brute force, ...)
- **Template frequency** — how rare this message pattern is *within the current batch*
  (numbers/IPs normalized out, e.g. `user_482` → `user_<NUM>`), so rare/unusual messages
  stand out even without a keyword match
- **Events per minute** — burst detection (useful for brute-force / flood-style attacks)
- **Off-hours flag** — whether the event happened outside business hours

## Explainability

Every flagged line comes with a lightweight "why" — the features that deviate most
(in standard deviations) from the training distribution, e.g.
`keyword_score (z=+2.8), template_frequency (z=-2.1)`. No SHAP dependency required,
but the same idea.

## Project structure

```
log_anomaly_project/
├── core/
│   ├── parser.py             # raw log text -> structured records
│   ├── feature_extractor.py  # structured records -> numeric feature matrix
│   └── model.py               # train/evaluate/save/load models, explainability
├── data/
│   ├── train_logs.csv        # synthetic labeled data (evaluation only)
│   └── sample_upload.log     # unlabeled sample file to try the upload feature
├── results/                   # saved model, scaler, metrics (generated by training)
├── static/style.css           # UI styling
├── templates/                 # Flask HTML templates
├── generate_logs.py           # synthetic data generator
├── train_and_evaluate.py      # training + model comparison pipeline
├── main.py                    # Flask app (upload -> analyze -> results)
└── requirements.txt
```

## Setup

```bash
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

## Run it

```bash
# 1. Generate synthetic training data
python generate_logs.py

# 2. Train and compare models (prints a metrics table, saves the best model)
python train_and_evaluate.py

# 3. Start the web app
python main.py
```

Open **http://localhost:5000**, upload `data/sample_upload.log` (or your own log file
in `YYYY-MM-DD HH:MM:SS LEVEL message` format), and view the flagged anomalies,
summary chart, and downloadable CSV of results.

## Known limitations (worth mentioning in an interview)

- Synthetic data, not real production logs — real logs would need a parser adapted
  to the actual log format in use (e.g. Apache/Nginx/syslog).
- `template_frequency` and `events_per_minute` are computed *relative to the current
  batch*, so very small uploads (a handful of lines) give noisier signal than larger ones.
- Isolation Forest's `contamination` parameter (expected anomaly rate) is a tunable
  assumption — it should be re-estimated for a new environment rather than reused blindly.
- This flags *statistical* anomalies, not confirmed malicious intent — it's a triage
  tool for a human analyst, not an autonomous blocker.

## Possible extensions

- Swap in an autoencoder (reconstruction error as anomaly score) for comparison
- Add SHAP for richer explainability
- Stream logs in near-real-time instead of batch upload
- Aggregate by source IP/user for stronger brute-force detection
